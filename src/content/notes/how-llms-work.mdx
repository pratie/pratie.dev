I use language models every day, and I learned the theory a few years ago. Every time I come back to it I understand it a little differently, which is a polite way of saying I never understood it properly. These notes are me writing it down until it stops moving.

This first one is the map. It follows one sentence through a real model, from the first character to the next word. Later notes zoom into one stage at a time and link back here.

The model is GPT-2 small: OpenAI, 2019, 124 million parameters. GPT-3, a year later, was more than a thousand times bigger. But GPT-2 runs on my laptop, so every number on this page is real. I ran the model and saved what it did. Today's models are far larger and far better trained. The machinery is the same.

## The loop

A language model is a function. You give it a list of tokens. It gives back a probability for every token in its vocabulary: how likely each one is to come next.

That is all it does. It does not write a paragraph. To get a paragraph, you call the function, pick one token using those probabilities, put it on the end of the list, and call the function again.

## Tokens

The model cannot read letters. Its input is a list of integers, and a tokenizer does the translation. The vocabulary has to have a fixed size, which rules out the obvious choices. Whole words: there are too many, and a new word would have no number. Single characters: a tiny vocabulary, but every sentence becomes very long, and the model has to learn spelling before it can learn anything else.

The compromise is pieces of words, found by an algorithm called byte-pair encoding. Start with the 256 possible bytes as your vocabulary. Find the pair of neighbouring tokens that appears most often in your text and glue it into one new token. Repeat. Common words end up as a single token. Rare words stay as a few pieces. And nothing is ever unspellable, because the single bytes never leave the vocabulary.

<BpeFig>

**Byte-pair encoding, trained in your browser on the text of this page.** Drag the slider to zero to see raw bytes, then replay the merges. Words this page uses often fuse into one token. Type a word it has never seen and it stays in pieces.

</BpeFig>

GPT-2's tokenizer was built the same way on a huge pile of web text, and it stopped after 50,000 merges. That is where the vocabulary size comes from: 256 bytes, 50,000 merges and one special end-of-text token make 50,257.

This is what it does with our sentence, and with a few other strings:

**GPT-2's real tokenizer.** The dot is a space. The number under each piece is what the model actually receives.

A few things here leak into everyday work:

- The space belongs to the token after it. <Tok t=" hello" />, <Tok t="hello" /> and <Tok t="Hello" /> are three unrelated integers as far as the model is concerned.
- Rare words cost more. "Eiffel" is three tokens. So is my handle.
- Numbers get chopped wherever the merges happened to fall. <Tok t=" 2026" /> is <Tok t=" 20" /> and <Tok t="26" />, which is one reason arithmetic is harder for these models than it looks.
- Prices, context limits and speed are all counted in tokens. In English a token is about four characters, or three quarters of a word.

## Embeddings

An integer like 8765 means nothing by itself. It is not "more" than 412. So the first thing the model does is swap each token for a vector: one row from a big table. GPT-2's table has a row for every token and 768 columns. That is 38.6 million numbers, almost a third of the whole model.

Nobody fills in that table. It starts as random noise, and training nudges it until tokens that behave alike sit near each other.

<EmbedFig>

**51 rows of GPT-2's embedding table**, squashed from 768 dimensions down to two with t-SNE. The map is approximate: t-SNE keeps neighbours together and distorts everything else, and I nudged the labels apart so they can be read. The list underneath is exact, measured in all 768 dimensions against the whole vocabulary.

</EmbedFig>

Nobody told the model that Tuesday is a day, or that Paris has something to do with France. It worked that out because those tokens are useful in the same places.

Two things about this stage matter later.

This is only a starting point. The token <Tok t=" bank" /> gets the same row whether the sentence is about rivers or money. Sorting that out is the job of the next stage.

And the table knows nothing about order. GPT-2 keeps a second table with one row per position, and adds the position's row to the token's row. That second table has 1,024 rows, which is exactly why GPT-2 cannot read more than 1,024 tokens at once.

## The blocks

Now there is one vector of 768 numbers per token. The middle of the model is 12 blocks stacked on top of each other, all with the same design, and each block does two things to every vector.

### Attention: tokens read each other

Each token looks back over the tokens before it and pulls in what it needs. This is the only place where information moves between positions. It is how the vector sitting at <Tok t=" of" /> finds out that the sentence was about the Eiffel Tower.

A block has 12 attention heads working side by side, and each head learns its own habit of where to look.

<AttnFig>

**Real attention weights from five of GPT-2's 144 heads**, on our sentence. "9.8" means layer 9, head 8, counting from zero. The start token is an extra token I put in front, which is the usual way to run GPT-2.

</AttnFig>

Three things to take from this.

A token can only look backwards. During training the model has to predict every next token without seeing it, so everything to the right is hidden.

Most heads, most of the time, are doing nothing. Averaged over all 144 heads on this sentence, about two thirds of the attention lands on the start token. That is how a head says "nothing for me here".

The useful ones are specific. Head 4.11 always looks one token back. Head 9.8 sits idle until the sentence needs a place, then looks at the thing whose place it is.

How a head computes those weights, with queries, keys and values, is worked through with small numbers in [the from-scratch note](/notes/gpt-from-scratch#attention).

### The MLP: each token thinks alone

After attention, every vector goes through a small two-layer network by itself, with no contact with the other positions. If attention gathers information, this is where the model does something with it. Two thirds of each block's parameters live here.

### Each block adds, it does not replace

Neither step overwrites the vector. Each one adds its result to what was already there. So a token's vector is a running total that every block writes into, and that is what makes it possible to stack 12 blocks, or 100, without the signal getting lost.

You can watch the running total change. Take the vector at the last position after each block, and ask what the model would predict if it stopped right there:

<LensFig>

**Our sentence, decoded early after each of the 12 blocks.** This trick is called the logit lens. It is an approximation: the model was never trained to be read halfway through.

</LensFig>

For the first five blocks the best guess is <Tok t=" the" />. That is the commonest word after "of", and guessing it takes no understanding at all. Around block 6 it starts naming places. By block 10 it has narrowed things down to European capitals. Then the last two blocks make it *less* sure, and London drops from 35% to 7%.

I do not have a tidy explanation for that last part. The late layers of these models are known to adjust confidence, and the lens is rough. But the main point survives: the answer is not looked up anywhere. It is built, a little per block.

## Probabilities

After the last block, the vector at the final position is compared against every row of the embedding table. GPT-2 uses the same table on the way out as on the way in. That gives 50,257 scores, called logits: any size, positive or negative. Softmax turns them into probabilities by exponentiating each score and dividing by the total.

$$
p_i = \frac{e^{z_i / T}}{\sum_j e^{z_j / T}}
$$

The $T$ is temperature, and it is the main knob you get as a user. Dividing the scores by a number below 1 pushes them apart, so the favourite wins more often. A number above 1 squashes them together, and the long tail gets a real chance.

The other common knob is top-p. Sort the tokens from most to least likely, keep the smallest group whose probabilities add up to p, and throw the rest away before picking.

<SamplerFig>

**Real GPT-2 scores for three different contexts.** The last bar is every token outside the top ten, added together. The sliders only change how a token is picked. The model's scores stay the same.

</SamplerFig>

Things to try:

- **"Once upon a".** The model is 99% sure of <Tok t=" time" />, and temperature barely changes anything. The knobs only matter when the model is unsure.
- **The Eiffel sentence at temperature 1.** More than two thirds of the probability sits outside the top ten, and all 50,257 tokens can be picked. That is why the first figure wandered off to "Luxplier". Pull top-p down to 0.9 and only 722 tokens are left. The other 49,535 were sharing the last tenth of the probability between them. This is what the setting is for.
- **Temperature near zero.** Always the favourite. Repeatable, and as the third run showed, prone to loops.

Why softmax is written the way it is, and how it breaks when you code it naively, is in [the from-scratch note](/notes/gpt-from-scratch#softmax).

## Training

Everything so far describes a model that already works. All 124 million numbers in it, the embedding tables, every attention head, every MLP, start out random. Training is how they get their values, and the idea is simple.

Take a real sentence. At every position, ask the model for its probabilities, and look up the probability it gave to the token that actually came next. High is good. Low means the model was surprised. The amount of surprise, −ln(p), is called the loss.

<SurprisalFig>

**GPT-2 reading a finished sentence**, scored at every position at once.

</SurprisalFig>

Read it left to right. <Tok t=" E" /> was a surprise, because almost anything can follow <Tok t="The" />. <Tok t="el" /> was not: after <Tok t=" E" /> and <Tok t="iff" /> it could hardly be anything else. And <Tok t=" Paris" /> gets its 6.9%, exactly as in the first figure.

Then comes the part that makes it learning. Calculus tells you, for every one of the 124 million numbers, which way to nudge it to make that loss a little smaller. Nudge them all. Repeat on billions of sentences. Nothing else is going on: no rules, no grammar, no table of facts. Whatever the model knows is whatever turned out to be useful for making the next token less surprising.

A chat model has one more stage. After this pretraining it is trained further on conversations and on human feedback, so that the most likely continuation of a question is a helpful answer.

## What this explains

Once the loop is clear, a lot of everyday behaviour stops being mysterious.

**Hallucination.** The model produces what is likely. For most questions, likely and true line up, which is why any of this works. When they come apart, nothing in the loop notices.

**No memory.** The function takes tokens and returns probabilities. It keeps nothing between calls. A chat "remembers" because the app sends the whole conversation back in, every time.

**The context window.** The list has a maximum length: 1,024 tokens for GPT-2, hundreds of thousands for current models. Everything the model knows about your situation has to fit inside it. The system prompt, your documents, tool results and the conversation so far are all just tokens in the list.

**Output is slow and costs more.** The model reads all the input tokens in one pass. Output tokens come out one pass each. That is why answers stream, and why APIs charge more for output than for input.

**Same prompt, different answer.** Picking is random on purpose. The dice are part of the design.

**Tool calls.** The model writes text in a format your code agreed to parse. The model never runs anything. Your code does, and then puts the result back into the list.
