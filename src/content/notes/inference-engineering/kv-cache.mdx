Something about the generation loop looked wasteful to me once I thought about it.

By the time a model writes its 1,000th token, it has already been through the first 999. It went through them to write token 999. And to write token 998. And every time before that.

Does it really process all of them again for each new token? Nothing about those earlier tokens has changed. So why not keep the results and reuse them?

That is the KV cache. But to see what exactly is being kept, I need two words from attention first.

## What a new token needs from the old ones

Attention is where a token reads the tokens before it. [The from-scratch note](/notes/gpt-from-scratch#attention) builds it up slowly. The short version:

- The token doing the reading produces a **query**. Think of it as a question.
- Every token produces a **key**, which is what it can be found by, and a **value**, which is what it hands over when it is read.

To write the next token, the model compares the newest token's query against the key of every earlier token, and blends their values according to how well each key matched.

So the newest token needs two things from each earlier token: its key and its value.

## The observation

Here is the part that makes the cache possible.

A model like GPT can only look backwards. That is the mask from the from-scratch note. So the key and the value of the fifth token depend only on the first five tokens. Whatever gets written afterwards, the sixth token, the six-hundredth, cannot reach back and change them.

Once computed, they are fixed for good.

So compute each token's key and value once, when the token first goes through the model, and store them. From then on, a new token only has to compute its own, and look the others up.

One key and one value per token, for every layer of the model. Keys and values: the **KV cache**.

Without the cache, the cost of each token grows with everything written so far. Double the length of a text and the total work roughly quadruples. With the cache, each new token costs about the same as the one before.

## How much does it save?

I wrote the same text with GPT-2 on my laptop twice: once feeding only the newest token and reusing the cache, and once switching the cache off and feeding the whole text back in for every token.

This is so effective that nobody runs without it. Every inference engine uses a KV cache by default. In fact, "prefill" from [chapter 5](/inference-engineering/prefill-and-decode) could just as well be called "filling the cache": reading the prompt means computing the keys and values for every token in it, ready for decode to use.

## What it costs

The saving is paid for in memory, and the amount surprised me.

For every token, the model stores a key and a value at every layer. In GPT-2 small that is 2 × 12 layers × 768 numbers, about 18,000 numbers per token. In a large model it is closer to 160,000.

Eight conversations of 32,000 tokens on a 70-billion-parameter model need about 84 GB for the cache alone. At 8 bits per weight, the model itself is 70 GB. The cache has become bigger than the model.

That explains several things from earlier chapters at once. It is why [a GPU needs headroom](/inference-engineering/gpus) well beyond the size of the weights. It is why long conversations are hard to serve. And it is why [quantizing](/inference-engineering/quantization) the cache is tempting even though it is riskier than quantizing weights: halving it frees a lot of room.

## Reusing it between requests

So far the cache lives and dies with one request. The next idea is to keep it around.

If two requests begin with exactly the same text, then the keys and values for that shared beginning are identical. The second request can skip reading it and start from the saved cache. This is called **prefix caching**.

It comes up constantly:

- A long system prompt that is sent with every request.
- The same document, with a different question each time.
- A codebase that is passed in again for every completion.
- Any chat. [A model has no memory](/notes/how-llms-work#what-this-explains), so every turn resends the entire conversation, and all of it except the newest message has been read before.

There is one strict rule, and it follows from the observation above. A token's key and value depend on everything before it. Change one early token and every token after it is different, as far as the model is concerned. So only a shared **beginning** can be reused, and it ends at the first token that differs.

**The same two requests, laid out two ways.** Yellow is what the second request can take from the cache. A made-up example, with one word per token.

</PrefixFig>

This turns into very practical advice for writing prompts. Put the parts that never change at the top. Put whatever is different each time, the user's question, the date, their name, at the bottom. A timestamp on the first line of a system prompt quietly throws away the whole cache on every single request.

It also explains a line on API price lists. "Cached input tokens" are cheaper because, for the provider, they really are almost free.

## Where to keep it

A cache that is this valuable and this large raises a storage question. An engine sets aside a share of the GPU's free memory for it. That share fills quickly, and then old entries have to be thrown out to make room. Every entry thrown out is a future request that has to read its prompt all over again.

So the cache spills outward. The book describes four places to keep it, each slower to reach and much roomier than the one before: the GPU's own memory, the ordinary RAM of the machine the GPU sits in, a local SSD, and storage out on the network. The first moves terabytes a second and holds tens to hundreds of gigabytes. The last moves a few gigabytes a second and holds tens of terabytes.

The idea is the same as any cache: keep what is used most where it is quickest to reach, and push the rest further out.

It also changes how requests should be shared out between servers. If several copies of the model are running, a user's next message should go back to the copy that already holds their conversation. Sending it to whichever server is least busy means reading the whole conversation again from the start. This is called cache-aware routing, and it comes back in [chapter 13](/inference-engineering/autoscaling).

The outermost level has a second use. A cache kept on network storage can be shared by every copy of the model, so a conversation is not lost when the server that held it is shut down.

## When the text gets very long

At some length the cache itself becomes the problem. The book has a nice definition of "long context" here: it is whatever length makes the cache start causing trouble on your setup, often somewhere past 32,000 tokens.

Two helpers are worth knowing by name. **PagedAttention** stores the cache in small fixed-size pages, so memory is not lost to awkward gaps. **Chunked prefill** reads a very long prompt in pieces, letting other users' tokens through in between, so one enormous request does not freeze everyone else.

And when a single GPU cannot hold the weights and the cache together, the model has to be spread over more than one. That is the next chapter.

## Where this leaves us

Each token's key and value never change after they are computed, so they are computed once and kept. That turns writing from something that gets slower with every token into something that stays roughly flat. The price is memory, often more than the model itself. And because only a shared beginning can be reused, the order of your prompt decides how much you save.
