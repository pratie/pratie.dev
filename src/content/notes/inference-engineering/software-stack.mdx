Here is something that looks strange at first. If I download an open model and run the sample code from its page, it works, and it is slow. The same model from a good provider, on the same kind of GPU, can be several times faster.

Same weights. Same chip. So where does the difference come from?

It comes from the software in between. There is a whole stack of it, and where you choose to work in that stack decides how much speed you get and how much effort it takes.

## Kernels: the code that touches the chip

The word "kernel" sounds deeper than it is. The book has a blunt translation that helps: when you read "CUDA kernel", read "a piece of code written for an NVIDIA GPU".

A kernel does one job. Multiply these two matrices. Apply this function to every number in this array. Its whole purpose is to split that job across the GPU's thousands of workers and waste as little as possible.

**CUDA** is the system NVIDIA provides for writing kernels and running them. It is not a programming language. Kernels are usually written in C++. But it is the foundation that everything else stands on, and it is a large part of why NVIDIA is so hard to compete with. A rival chip needs its own version of all of this.

Almost nobody writes kernels from scratch. They come in libraries. The most heavily used one in inference is the kernel for general matrix multiplication, because that is what every linear layer in a model boils down to. You will see it shortened to GEMM, and NVIDIA's standard collection of such kernels is called cuBLAS.

What surprised me is how tied a kernel is to one specific chip. A good one is written around the exact amount of fast memory and the exact layout of a particular GPU. The book notes that FlashAttention for an H100 is different code from FlashAttention for a B200. This is why a brand new GPU does not reach its full speed on day one. The kernels have to catch up.

So part of the job is choosing kernels, and mostly the software does it for you. Frameworks and engines arrive with a kernel already picked for each operation on each kind of GPU. Now and then it pays to overrule one by hand. The book's example: when the DeepSeek lab released one of its models, it also released its own matrix-multiplication kernels for 8-bit numbers on one generation of GPU, quicker than the standard ones for that case. You can plug a kernel like that in for a single step of a model. The price is that whether it still works on the next GPU is now your problem.

## Same maths, different speed

How can two pieces of code that compute the same thing differ so much in speed? [Chapter 5](/inference-engineering/prefill-and-decode) already gave the answer: fetching data from memory is the slow part.

Suppose you need to do three things to a big array of numbers: multiply by something, add something, then replace the negatives with zero. That happens to be what a layer of a neural network does.

The obvious way is three steps. Each one reads the whole array from memory, changes it, and writes a whole new array back.

The other way is to do all three things to each number while it is on the chip, and write it back once. Combining operations like this is called **kernel fusion**.

I tried both on my laptop, on an array of {fusion.megabytes} MB.

Simple cases like this can be fused automatically by a compiler. The complicated ones are fused by hand, by people who know one chip very well. FlashAttention is the famous example: the same attention arithmetic, rearranged so that intermediate results never leave the chip's fastest memory.

## PyTorch: describing the model

One layer up is the **framework**. In practice that means PyTorch.

PyTorch lets you write a model as ordinary Python: this layer, then that function, then this layer. It works out which kernels to call and where the data needs to go.

It also has a **compile** step. You point it at a specific GPU and it picks kernels and fuses what it can for that chip. The book mentions one limit: it cannot fuse the hand-written kernels that you plug in from outside, and for language models those are exactly the important ones.

Two smaller things at this layer are worth knowing.

**Model files.** Weights are usually shipped as *safetensors* files. The name is literal. Older formats could run arbitrary code when you opened them, and this one holds nothing but numbers. Another format, ONNX, stores the weights together with a description of the model's structure, which makes a file more portable between tools.

**Runtimes.** A file like that can be handed to a program built only for running models. ONNX Runtime is the open one and works on many kinds of hardware. TensorRT is NVIDIA's, and it compiles the model into something tuned for one particular NVIDIA GPU. For language models this middle step is going out of fashion, and people go straight from PyTorch to an engine. The book says TensorRT is still widely used for image and video models.

**Reference code.** The `transformers` library from Hugging Face is what the sample code on a model's page uses, and `diffusers` is its twin for image models. The book is clear about what they are for: a correct, readable implementation to learn from and adapt. It was never meant for serving at scale.

That, by the way, is what I used for every measurement in this series. So my numbers are the slow version on purpose.

## Where does a pass spend its time?

Before going further up, I wanted to see inside one pass. A **benchmark** tells you how long something took. A **profiler** tells you where that time went.

Two things stood out.

More than four fifths of the time is matrix multiplication. That is the whole reason one kernel, the matrix-multiply kernel, gets so much attention.

And the second row is waste. The reference code works out a score for every token in the vocabulary at every position of the prompt. Only the scores at the last position are needed to pick the next token. A real engine skips the rest. I would not have guessed that a quarter of the time was going there, and that is the point of profiling. You find the thing you did not think to look for.

The book lists three profilers. One is built into PyTorch, and it is the one I used. The other two come from NVIDIA and look at the GPU itself: one across a whole system, one inside a single kernel. It also says most inference engineers will rarely open any of them. If you run a ready-made engine, your work is a loop of changing settings and benchmarking. Profiling is for people who write their own serving code, or who work on the engines.

## Engines: where most of the work happens now

An **inference engine** is a complete server for a model. You give it weights and a configuration. It gives you an API, and inside it are the techniques from this series, already written and tested: batching, the KV cache, quantized weights, speculation, splitting across GPUs.

This is the layer most inference engineers work at. The job becomes choosing an engine and tuning its settings, not writing kernels.

The book compares three, and the comparison comes down to one trade. Two of them are easy to pick up and will run almost any model. The third takes real effort, supports fewer models, only works on NVIDIA GPUs, and is usually the fastest.

**vLLM** is the most widely used. It supports the most models and the most kinds of hardware, including chips that are not NVIDIA's, and a new open model usually works in it on the day of release. It is the one to reach for when you want something running quickly.

**SGLang** is the other community-built engine, for NVIDIA and AMD GPUs. It has put a lot of work into very large Mixture of Experts models spread over many machines, and it is built so that you can swap out individual parts.

**TensorRT-LLM** is NVIDIA's. It is usually the fastest, partly because it has access to kernels written by NVIDIA's own engineers, and it takes the most effort to set up. One trap in the name: it began as an add-on to the TensorRT runtime from the section above, and since its version 1 it no longer uses TensorRT at all. The book's author says his team uses all three engines, and this one most.

There is a principle running through that comparison which the book states outright and which I keep noticing everywhere in this subject. The more you constrain a system, the faster it can go. The engine that supports everything is rarely the fastest at any one thing.

## Above the engine

One layer remains. Once you have many engines on many machines, something has to coordinate them: send each request to the machine that already holds its cache, split reading and writing onto different machines, spread a model across more than one box.

NVIDIA's **Dynamo** does this and sits on top of any of the three engines. The book is direct about when you need it. It is built for very large models and very heavy traffic. Below that scale it is extra complexity for little gain, and you should use an engine directly.

## Where this leaves us

The difference between slow sample code and a fast provider is this stack. Kernels decide how well each operation uses the chip. The framework chooses and combines them. The engine adds every technique in this series. And for most people, most of the time, the engine is the right place to work, with enough understanding of the layer underneath to know what its settings are doing.
