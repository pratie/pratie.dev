When I call a model through an API, it feels like nothing much is happening on the other side. I send some text and words start coming back. To build a product, that is all you need to know.

Then the small questions start. Why does the first word take half a second while the rest arrive quickly? Why is the same model fast from one provider and slow from another? Why do output tokens cost more than input tokens? And if open models are free to download, why is running one yourself considered hard?

All of these have the same answer, and it has a name: inference.

## Two phases in a model's life

A model lives in two phases.

**Training** is where the model's numbers, its weights, get their values. It happens once per model, takes weeks, and uses thousands of GPUs.

**Inference** is using those finished weights to answer a request. It happens every time someone presses Enter.

In [the basics note](/notes/how-llms-work) I followed one sentence through GPT-2. Everything in that note was inference. The weights were already there and the model only had to use them.

The thing to notice is the difference in scale between the two. Training is a large project with an end date. Inference is the thing that runs every second of every day for as long as the product exists. The book opens by arguing that this is where most of the value in AI now sits, and once you look at it this way the claim is not surprising. Every useful thing a model does for anyone is an inference call.

## Why can't I just put the model on a GPU?

This is the honest first question. The model is a file. A GPU can run the file. What else is there to do?

So let's try it in our heads. One GPU, one model, writing 50 tokens a second. One person asks a question that needs a 300-token answer. That takes six seconds. Fine.

Now forty people ask at the same moment.

Taken one at a time, the fortieth person waits four minutes. Nobody waits four minutes for a chatbot.

You can do much better by running several requests through the model together, which is called batching. I get to why that works in [chapter 5](/inference-engineering/prefill-and-decode). For now, look at what it costs. Each individual answer gets slower, and the crowd as a whole is served far sooner. That is a trade: speed for one person against speed for everyone. Which side you favour depends on what you are building.

And we have not even asked the next question. What if four hundred people turn up? No batch size saves a single GPU then. You need more GPUs, something to decide which request goes to which one, and something to start machines when traffic rises and stop them when it falls, because a GPU costs dollars an hour whether it is busy or idle.

So "just put it on a GPU" breaks in three places. One request can be too slow. Many requests do not fit. And traffic never stays the same for long.

Most of what sounds exotic lives in the runtime layer. Most of what keeps people awake at night lives in the infrastructure layer. A fast server that falls over under load is not a fast service.

## The toolbox

On the runtime side there is a short list of techniques that come up again and again. Here is each one in a line. Every one of them gets a chapter later.

- **Batching.** Run several requests through the model together, so the GPU's spare capacity is not wasted.
- **Caching.** The model repeats a lot of work from one token to the next, and from one request to the next. Save it and reuse it.
- **Quantization.** Store the weights with fewer bits each. Smaller numbers are quicker to move and quicker to multiply.
- **Speculation.** Let something cheap guess the next few tokens, and let the big model check all the guesses at once.
- **Parallelism.** Spread one model across several GPUs when it does not fit on one, or when one is not fast enough.
- **Disaggregation.** Reading the prompt and writing the answer stress a GPU in different ways, so give each its own machines.

None of these changes what the model knows. They change how much time and money it takes to get the same answer out.

## Why this is suddenly everyone's problem

For a while it looked as if only a few labs would ever need any of this. They would train the models and serve them from behind an API, and the rest of us would rent intelligence one token at a time.

What changed is that open models got good. You can download weights that are close to the best closed models and run them on hardware you control. The book's argument is that doing so gives you three things an API cannot: you decide how fast it is, how reliable it is, and what it costs.

I think that argument is mostly right, with a caveat. The author works at Baseten, a company that sells exactly this, so he is not neutral on whether you should do it. He is also clear that most products should start on a pay-per-token API and move only when there is a reason. [Chapter 2](/inference-engineering/know-your-workload) is about telling when that is.
